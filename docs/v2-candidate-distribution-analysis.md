# R4-A0：候选指标分布分析

> 本文记录轻量候选池编码前的数据基线、指标口径和冷启动约束。它是 R4-A 的准备工作，
> 不生成持久化候选、投资信号或 Telegram 通知。

R4-A0 在 R3 的 24 小时观察期间并行完成，只增加离线只读分析能力；没有迁移数据库、替换线上
二进制、重启服务或启用 V2 reporter，因此没有绕过 R3 的线上运行门禁。

## 2. 目标与边界

本阶段回答：

1. Crypto 与 TradFi 的 `15m`、`1h` 收益实际分布如何；
2. 冷启动收益门槛在每个五分钟窗口会产生多少候选；
3. 原始候选集合的换手有多快，是否必须加入滞回；
4. 成交额、量能倍数、连续性和高点回撤的分布能否支持下一阶段定阈值；
5. 七天全量分析的查询时间和内存规模是否适合在 jmk 执行。

明确不做：候选落库、深度接口采集、评分、生命周期、Telegram、自动交易和根据七天样本宣称
策略有效。

## 3. 命令与模块

```bash
binance-monitor candidate-analysis \
  --env-file /absolute/path/.env.v2 \
  --lookback 168h \
  --format markdown
```

- 默认结束时间为数据库内 `returns-v1` 最新完整五分钟时点；可用 `--end` 指定 UTC RFC3339
  五分钟时点；
- `--lookback` 限制为 1 小时至 14 天，默认 168 小时；七天实测峰值约 612 MiB，限制上界以
  避免一次性研究查询占用数 GiB 内存；
- `--format` 支持 `markdown` 和 `json`；
- 命令只执行 `SELECT`，不请求 Binance、不写 PostgreSQL、不调用 Telegram。

代码边界：

- `internal/candidateanalysis`：分析模型、分布计算、候选模拟和渲染；
- `internal/storage/postgres/candidate_analysis_repository.go`：只读 SQL；
- `internal/v2/command/candidate_analysis.go`：Cobra CLI 适配；
- `internal/candidateanalysis/service_test.go`：分位数、候选换手、缺口和渲染测试；
- `internal/storage/postgres/candidate_analysis_repository_integration_test.go`：真实 PostgreSQL
  类型、窗口函数和闭合 K 线边界测试。

本阶段没有新增第三方依赖。生产行情和收益继续以 PostgreSQL `numeric` 与
`shopspring/decimal` 为事实口径；离线分布查询显式转换为 `double precision`，只用于统计展示，
不得反写为生产行情或信号证据。

## 4. 指标定义

| 指标 | 定义 | 防错条件 |
| --- | --- | --- |
| 15m/1h 收益 | 已落库且质量有效的滚动收益 | 两周期都有效才进入候选模拟 |
| 15m 加速度 | 当前滚动 15m 收益减去恰好 15 分钟前的滚动 15m 收益 | 时间不连续则不计算 |
| 上涨宽度 | 每板块、每五分钟窗口收益大于 0 的标的占比 | Crypto/TradFi 分开统计 |
| 横截面阈值 | 每窗口 Crypto/TradFi 各自的 15m P95、1h P90 | 不跨板块比较 |
| 原始候选 | 15m ≥ max(P95, 绝对门槛)，或 1h ≥ max(P90, 绝对门槛) | 尚未应用流动性门槛 |
| 换手率 | 相邻完整五分钟候选集合对称差 / 并集 | 中间缺窗口时不比较 |
| 量能倍数 | 当前闭合 15m 成交额 / 前 20 根闭合 15m 成交额中位数 | 20 根必须连续且中位数大于 0 |
| 连续收盘上涨 | 连续 `close[t] > close[t-1]` 的 15m 区间数 | K 线缺口立即重置 |
| 1h 高点回撤 | 当前收盘 / 最近四根闭合 K 线最高价 - 1 | 只使用当前及过去闭合 K 线 |

## 5. 七天实测结果

样本包含 2,017 个五分钟窗口：Crypto 1,126,974 行有效 feature、379,131 根分析区间内
闭合 K 线；TradFi 282,375 行有效 feature、114,976 根闭合 K 线。

### 5.1 关键分布

| 板块 | 15m 收益 P95 | 1h 收益 P95 | 15m 横截面 P95 的时间中位数 | 1h 横截面 P90 的时间中位数 | 1h 成交额 P25 | 24h 成交额 P25 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Crypto | 1.0118% | 1.9865% | 0.7436% | 0.9663% | $53,524 | $1,747,376 |
| TradFi | 0.4593% | 0.9327% | 0.2956% | 0.3815% | $14,400 | $602,854 |

| 板块 | 量能倍数 P50 / P90 / P95 | 1h 高点回撤 P50 / P90 | 连续收盘上涨 P50 / P90 |
| --- | ---: | ---: | ---: |
| Crypto | 0.9691 / 2.7355 / 3.9734 | -0.6581% / -0.1338% | 0 / 3 |
| TradFi | 0.9482 / 6.4410 / 12.7603 | -0.2096% / -0.0244% | 0 / 2 |

TradFi 的量能倍数长尾显著高于 Crypto，主要原因可能是部分合约基准成交额很低。因此后续不能
只用“量能倍数高”作为确认，必须先通过绝对流动性门槛，并对评分输入做有上限的变换。

### 5.2 冷启动候选模拟

模拟沿用台账中的绝对门槛：Crypto `15m +1.5% / 1h +3.0%`，TradFi
`15m +0.5% / 1h +1.0%`。

| 板块 | 每窗口候选 P50 | P90 | P95 | 最大 | 七天唯一标的 | 五分钟换手率 P50 | P90 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Crypto | 13 | 33 | 42 | 75 | 545 | 53.85% | 75.00% |
| TradFi | 5 | 17 | 19 | 26 | 164 | 60.00% | 100.00% |

这证明收益条件适合做高召回的“发现层”，但不能直接作为通知或深度采集名单：强行情时会超过
容量，五分钟原始集合也过度抖动。

## 6. 对 R4-A1 的约束

1. 保留当前收益门槛作为 `candidate-rules-v1` 的冷启动发现条件，不宣称它已经有正收益优势。
2. 冷候选容量先按 Crypto 20、TradFi 10 设计；超额时以结构化优先级选择，而不是修改原始事实。
3. 进入结果和“被容量截断”结果必须分别审计，避免把未进入误解释为未触发。
4. 活动候选暂定连续 3 个五分钟窗口未命中才退出，并设置 30 分钟冷却；具体参数在
   24–48 小时影子统计后发布新规则版本调整。
5. 流动性敏感性起点暂定 Crypto `1h ≥ $50k 且 24h ≥ $1m`、TradFi
   `1h ≥ $15k 且 24h ≥ $500k`；R4-A1 必须先输出门槛前后候选数量与排除原因，才能决定是否生效。
6. 量能倍数 `≥1.5` 只作为确认/优先级证据，不作为发现层的唯一必要条件；极端值必须截尾或
   对数化后才能进入后续评分。
7. 候选优先级不是投资分数。R4-A 只负责缩小深度采集范围，R5/R6 才负责证据评分和结果评估。

## 7. 局限与下一步

- 七天样本只覆盖一个短市场区间，不能代表牛市、熊市和低波动市场；
- 当前模拟没有应用流动性门槛、候选容量和滞回，因此候选数量是发现层上界；
- 五分钟滚动收益窗口相互重叠，不能把全部 2,017 个窗口当作独立统计样本；
- 合约状态按当前事实表过滤，历史交易状态的精确 event-time 还需依赖后续状态有效期数据积累；
- 没有 T+1h/T+4h/T+24h、MFE、MAE，因此不能判断这些条件是否有投资收益。

R3 完成 24 小时连续验收后，下一开发项是 R4-A1：版本化候选领域模型、流动性敏感性统计、
容量截断、延续/退出滞回、幂等 PostgreSQL 事实与审计。候选任务正式影子部署仍需独立验收。
